# 第一次复盘：以前没有先选架构

记录日期：2026-09-22

## 我当时是怎样开始的

做之前的项目时，我没有先系统比较架构，也不熟悉 MVVM 等名称。通常是从想做的功能开始，边实现边理解。现在回看代码，可以描述它们已经形成的结构；但不能把今天的理解写成当时已经做过的设计决策。

我目前不能仅凭仓库文件确定每个技术选择最早由谁提出、当时比较了哪些候选方案。以后需要区分：**当时真实做过的选择**、**现在从代码中观察到的结构**、**回看后才想到的改进**。

这些是**改进候选**，不是已经证实的代码错误。其他公开仓库中的 fork 也不作为我原创项目的设计证据。

## 我学到的事

1. 没有预先给架构命名，项目也可能逐步形成可工作的结构；但我需要知道每部分负责什么、数据怎么走、失败时会怎样。
2. 回看旧项目时先问“目标用户能否完成核心任务”“证据是什么”，不要只因刚学会某个模式就重写代码。
3. 新项目开始时，我可以先说明用户、核心流程、验收标准和约束，再让 AI 调查并提出最简单的设计。对会改变业务结果、安全边界或成本的选择，我要理解理由并确认。
4. 每次记录当时不知道什么、AI 建议了什么、我怎样查证与验证。事后认识到的理由要标明是**复盘**，不能冒充最初的决策过程。

## 下一次实践

先选一个已有项目的一条真实用户流程，写出可观察的验收标准，再做一次使用验证。把观察结果和是否修改的理由补进仓库；在有证据之前，不为了“换成更先进的架构”而改代码。
